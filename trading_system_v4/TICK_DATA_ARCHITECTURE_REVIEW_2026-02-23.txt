0.5  Remaining Known Gaps (not yet fixed)
------------------------------------------
A. ExecutionEngine.send_order() does not submit real IBKR orders.
   The broker_api stub is in place; a real implementation is needed.

B. Feature schema assertion not yet added.
   V4ModelInference enforces feature ordering from JSON, but there is no
   explicit runtime check that the live feature dict keys exactly match
   the saved feature list.  Missing keys silently get 0.0 (documented
   behavior, but a hard assertion on startup would be safer).

C. No walk-forward threshold tuning.
   Threshold is selected once on the last CV fold.  A proper walk-forward
   optimization maximizing expectancy over a held-out test period is needed
   before live capital deployment.

D. Fixed 1-pip spread penalty in labeling does not match real regimes.
   London open / NFP / FOMC spreads can be 3-10x wider.  This may bias
   labels and overstate edge during high-volatility periods.

E. No feature/label drift monitoring in live.
   No ongoing comparison of live tick-bar feature distributions vs the
   training distribution.  PSI or KS tests should be added.

F. Parity ratio should be re-estimated periodically.
   The 7.85x ratio was measured on one hour of one day in February 2026.
   IBKR tick density changes with market activity and algo upgrades.
   Re-run check_tick_parity.py monthly.

1) My Understanding of How the Trading Algorithm Is Intended to Work
--------------------------------------------------------------------
A. Data Layer (offline)
1. Download raw Dukascopy tick data month-by-month.
2. Build fixed-size information-driven bars (1000 ticks per bar).
3. For each bar compute:
   - OHLC midpoint prices
   - avg_spread, max_spread
   - vol_imbalance (ask_volume - bid_volume)
   - buy_volume, sell_volume, total_volume, buy_ratio
   - tick_velocity (ticks/sec from bar duration)
4. Append bars into a master parquet dataset:
   trading_system_v4/data/eurusd_1000t_bars.parquet

B. Labeling Layer (offline)
1. Generate base trade signals using EMA crossover on tick bars:
   - Bull cross => signal = +1
   - Bear cross => signal = -1
2. Simulate each signal with path-dependent TP/SL over next 100 bars:
   - TP = 1.5 * ATR
   - SL = 1.0 * ATR
   - Spread penalty fixed at 1 pip (0.00010)
3. Meta-label outcome:
   - y_meta = 1 if TP hit first
   - y_meta = 0 if SL hit first
4. Engineer feature set at signal points, including microstructure:
   - tick_velocity_ratio
   - spread_ratio
   - vol_imbalance_sma5
   - liquidity_shock
   - order_flow_toxicity
   - micro_trend_alignment
   - price_vol_divergence
   - plus time and volatility context
5. Save labeled dataset:
   trading_system_v4/data/meta_labeled_1000t.parquet

C. Model Layer (offline)
1. Train XGBoost binary classifier to estimate P(win | signal context).
2. Use TimeSeriesSplit CV, report AUC/Precision/Recall at threshold=0.65.
3. Train final model on all data and save artifacts:
   - trading_system_v4/model/meta_model_ema_eurusd.pkl
   - trading_system_v4/model/meta_model_ema_features.json

D. Live Execution Layer (intended)
1. Subscribe to live IBKR bid/ask ticks.
2. Aggregate live ticks into N-tick bars with crash-safe state recovery.
3. Compute same feature schema used in training.
4. Detect EMA crossover events live.
5. Score event with trained meta-model probability.
6. Execute only when probability > threshold.

E. Parity Layer
1. Compare Dukascopy vs IBKR tick density on same 1-hour window.
2. Derive ratio and adjust live bar size so live feature dynamics match training regime.
3. Most recent observed ratio in your session: IBKR had far more ticks than Dukascopy.

3) Flaws, Gaps, and Risks I See
--------------------------------
Critical Gaps (must fix before real live use)
1. Missing model-to-live bridge:
   - I do not see a script/module that loads meta_model_ema_eurusd.pkl and uses it to approve/reject live EMA signals.
   - Current pieces exist, but the full inference path is not yet wired.

2. Feature parity risk between training and live:
   - Training uses derived features (rolling SMA-based ratios/divergence) that are not yet computed inside live_tick_aggregator.py.
   - Aggregator currently emits primitive bar fields only.
   - Without a live feature builder that exactly reproduces training transforms, live predictions will be inconsistent.

3. No explicit feature schema/version lock:
   - There is no runtime guard that checks live feature columns/order/types against meta_model_ema_features.json.
   - Silent schema drift risk is high.

4. No calibrated decision policy beyond static 0.65 threshold:
   - Threshold appears fixed in training metrics, but no walk-forward threshold tuning or expected-value policy is defined.

5. No execution-cost model alignment:
   - Labeling uses fixed spread penalty (1 pip), but real spread/slippage are regime-dependent.
   - This can bias labels and degrade live edge.

Medium Priority Gaps
6. CV description mismatch:
   - train_meta_model.py docstring says “Purged K-Fold” and “calibrated probability model”.
   - Implementation is standard TimeSeriesSplit, not explicit purged/embargo CV, and no probability calibration stage is implemented.

7. Hardcoded date/config in parity tool:
   - check_tick_parity.py uses hardcoded TARGET_DATE and static host/port/clientId.
   - Better to parameterize via env/CLI for repeatable operations.

8. Potential timezone/naive datetime assumptions:
   - Dukascopy fetch uses naive datetime interpreted as UTC by convention.
   - Works if consistently respected, but fragile without strict utility wrappers.

9. Tick volume semantics mismatch risk:
   - “ask_volume/bid_volume” from Dukascopy and bid/ask sizes from IBKR are not identical market microstructure proxies.
   - Cross-source feature meaning may differ.

10. No monitoring for feature/label drift:
   - No ongoing live-vs-train drift checks on feature distributions or win-rate decay.

Operational Notes
11. check_tick_parity.py had event-loop friction during foreground execution in your session (KeyboardInterrupt / loop closed behavior).
   - It can run, but wrapper hygiene should be improved for reliability.

12. download_tick_data.py currently has END_YEAR=2025 while current date is 2026-02-23.
   - This is fine for now if intentional, but do not forget to extend coverage if you want “up to present”.
